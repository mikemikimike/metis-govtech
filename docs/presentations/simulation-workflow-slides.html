The Simulation Turn Workflow

How a persona drives a target system, one turn at a time

Describes the design in issue #373 — approved in chat, not yet implemented.

Four roles

User Agent  ──decides──▶  Orchestrator  ──dispatches──▶  Runner  ──▶  Target System
(the persona)              (runs the loop,                (the only role
                            enforces the rules)             that touches
                                                             the real target)
  • User Agent — a persona, driven by an LLM, pursuing a goal against the target
  • Orchestrator — owns the run: dispatches, checks the rules, decides whether to continue
  • Runner — the adapter for one specific target; the only thing that touches it
  • Target System — whatever is under evaluation; METIS has no code for it

The Runner abstract class

class Runner(ABC):

    async def setup(config)                 — open the connection
    async def send_turn(message, actions)
                          -> Observation     — do the turn, report back
    async def teardown()                    — close the connection
    async def get_session_id()              — target's session id, if any
  • Every runner — Playwright, Orca's API, anything else — implements exactly these four methods, nothing more
  • send_turn is where the contract lives: its own docstring cites I1, I3, I4, I5 by name
  • A Runner knows nothing about personas, scenarios, or when to stop — only "here's a turn, tell me what happened"

What a turn is

  read last Observation ──▶ decide (a sequence of actions) ──▶ act
        ▲                                                        │
        └────────────────────── next turn ──────────────────────┘
  • One turn = one persona decision — not one transport call
  • A max_turns budget counts decisions, the same across every target
  • Underneath, a runner may do one request or several retries — invisible to the loop

Only two kinds are framework-provided: send a message and attach a file — because something outside the runner has to recognise them. Everything else is runner-private: a button, a form field, a shortcut.

The Action class hierarchy

                     Action
                       │
      ┌────────────────┼────────────────┐
      ▼                ▼                ▼
SendMessageAction UploadFileAction  (runner-private
                                     leaves — one per
                                     runner-specific
                                     control)
  • SendMessageAction, UploadFileAction — the caller must recognise these on their own
  • Everything else — PlaywrightFillAction, OrcaAnswerFormAction, … — nobody outside that runner ever sees it
  • A leaf may inherit both provided branches — one atomic step that both attaches a file and asks about it
  • An atom is atomic: if the fixture was never staged, the whole composite is withheld, prose included

The Action base class

class Action(BaseModel, extra="forbid"):
    type: str

    terminal: ClassVar[bool] = False   — ends the turn; default is "no"
    usage: ClassVar[str]                — persona-facing text, no default

class SendMessageAction(Action, extra="forbid"):
    type: Literal["send_message"] = "send_message"
    text: str

    terminal: ClassVar[bool] = True     — this one overrides the default
  • terminal defaults to False; a leaf overrides it to True only if choosing it ends the turn (I8)
  • usage has no default — a leaf that omits it raises AttributeError the moment anything reads it, which the startup check exploits to catch a persona-unexplainable action before any persona runs
  • extra="forbid" — a persona can't smuggle an unexpected field onto an action the runner never declared

A turn is an ordered, dependent sequence

  PlaywrightFillAction(name)
            │
            ▼
  PlaywrightFillAction(email)
            │
            ▼
  PlaywrightFillAction(amount)
            │
            ▼
  PlaywrightSubmitAction()      ◀── terminal: ends the turn

This runner's own classes (design section 10) — Orca's API runner uses OrcaAnswerFormAction/OrcaSubmitFormAction instead.

  • Actions run in the order the persona gave them — never reordered, never parallel
  • Each depends on the ones before: the first that doesn't land stops the rest
  • At most one action per turn is terminal, and it must be last
  • A terminal action is not required — an upload-only turn is legitimate

Worked example: five fields, one turn

PlaywrightFillAction(f1) ... PlaywrightFillAction(f5), PlaywrightSubmitAction() — sent as one turn, carried out in one round trip.

  • Six actions in, six result rows out — not six turns
  • If the target rejects f3, fields 4–5 and the submit are never attempted
  • The report shows exactly which field stopped the chain

What comes back

ChannelReports on
text, artifactswhat the target said and produced
action_resultsone row per action, each with its own outcome
available_actionswhat the target is offering next
status_labelsanything the reply raises that no single action explains

Kept separate on purpose — a rejected upload is never mistaken for a target outage.

Five outcomes, always in this shape

  delivered  delivered  delivered   failed   skipped   skipped
  └──────────── the chain ran ────────┘ └stop┘  └── never attempted ──┘

delivered went through  ·  failed attempted, didn't land  ·  withheld refused before trying  ·  unknown can't tell what happened  ·  skipped never attempted

At most one "stop" row per turn. Nothing but skipped follows it.

The invariants

A turn's shape

  • I1 — Completeness. Every action gets exactly one result row, in order. None vanish.
  • I2 — Minimal verdict. Every row's outcome is one of the five values — never a bare pass/fail.
  • I6 — Ordered dependence. Once one action fails to land, everything after it is skipped.
  • I8 — Terminal cardinality. At most one action ends a turn, and it comes last.

A runner's promises

  • I3 — Session usability. The connection stays usable next turn, or the runner says it doesn't.
  • I4 — Delivery multiplicity. A turn is carried out at most once — never re-sent.
  • I7 — Declared vocabulary. A persona can never be offered an action nothing can execute.

I5 is retired in this design — the number stays vacant.

Who checks what

Same eight invariants — ranked by how much you should trust each one

RuleInvariantEnforced by
Outcome is one of five values, never a booleanI2type system
One result row per action, in orderI1every turn, automatically
Outcomes form the ran → stopped → skipped shapeI6, I8every turn, automatically
A runner never declares an action it can't executeI7startup, once

The persona-facing explanation is actually clearnot numberedreviewer
  • Type system — can't even construct the bad value; no test or reviewer needed
  • Automatic, per turn / at startup — code checks it and raises on violation; caught the moment it happens, not baked into the type
  • Reviewer — nothing in the code checks it at all; a person reads the runner and judges whether the promise holds

I3 and I4 sit at the weakest tier — exactly the gap the next slide's conformance suite is aimed at closing.

Can we formalize this?

  RUNNING ──(delivered)──▶ RUNNING
     │
     └─(failed/withheld/unknown)─▶ STOPPED ──(skipped)*──▶ STOPPED

  every turn's outcome column matches:  delivered* (failed|withheld|unknown)? skipped*
  • Property-based tests — fuzz action sequences, assert the pattern always holds. Cheap, fits pytest.
  • A conformance suite — the same checks, packaged so any new runner proves itself. Already tracked.
  • A full formal model — worth it only if raise/recover bugs keep recurring across turns.
