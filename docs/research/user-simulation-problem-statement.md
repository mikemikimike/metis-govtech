# Problem Statement: METIS User Simulation

This document states a problem and asks for a design proposal. It does not prescribe a
solution. The section Ideas to consider collects ideas the team has discussed; they are
starting points, not requirements.

Read this document first. Then use [`user-simulation-kit/`](user-simulation-kit/) to get
started quickly: it holds Orca's personas, scenarios, tasks and fixtures in a simple
format a prototype can read directly, the output a simulator must produce, and the
prompts today's user agent is given. Orca is the first target to validate against, not
the only one the design must support.

References to issues (#306, #310, #320) are GitHub issues in
`govtech-responsibleai/metis`. `docs/runner-contract.md` is the normative set of rules
current runners follow; a few questions below ask the proposal to look at it and decide
what still applies.

## Terms

| Term | What it is | Status |
| --- | --- | --- |
| **Persona** | An input: who the simulated user is and how they behave (`specification.personas[]`). | Input |
| **Scenario** | An input: what the simulated user is trying to achieve (`specification.scenarios[]`). | Input |
| **Target** | The agentic system under evaluation, reached over its API or web UI. It writes its own traces to Langfuse. It belongs to another team, and METIS does not control it. Orca is the current target. | External system |
| **User agent** | The LLM that plays a persona (`simulation/user_agent/`). It decides *what* the simulated user says and does next, and when to stop. It never touches the target. | Exists today |
| **Runner** | The component that talks to the target (`simulation/runner.py` and `runners/`). It turns the user agent's message and actions into transport calls, and returns an observation of what the target did. Today each target needs its own hand-written runner. | Exists today |
| **Runner agent** | A proposed LLM inside the runner that would work out *how* to carry out an action on a given target, for example from its OpenAPI specification or its web page, replacing hand-written target code. | Proposal only (see Ideas to consider). The proposal may reject it |

"Persona" always means the input, never the LLM that plays it. The **orchestrator** is the loop that connects the user agent to the runner
and applies the stopping rules.

```
 persona + scenario ──▶ user agent ──message, actions──▶ runner ──transport──▶ target
                        (what to do)  ◀──observation───  (how to do it)
                                                         └ runner agent? (proposed)
         └──────────────── orchestrator: turn loop, stopping rules, record ─────────┘
```

## 1. Context

### What METIS is

METIS (Measurement and Evaluation of Trustworthy Intelligent Systems) tests agentic AI
systems, such as a chat assistant that hands work to specialist sub-agents, for safety
and quality. It does this in three steps, each a separate command:

1. **Write a specification.** A user describes what to test in a `specification.yaml`
   file: the behaviours to measure, the personas and scenarios to simulate, and the
   tasks that combine them. Files the simulated user may upload sit next to it in
   `fixtures/`. The specification can be written by hand, generated by an interactive
   command-line tool (`metis wizard`), or built in a browser app (`apps/web`). None of
   these are in scope here.
2. **Simulate** (`metis engine simulate`). A user agent plays each persona in
   conversation with the target, once per trial, and saves a record of each trial.
   **This document is about this step only.**
3. **Evaluate** (`metis engine evaluate`). For each trial, METIS fetches the target's
   own traces from Langfuse, an LLM observability service the target logs to, and
   scores them against the behaviours in the specification. It then writes a report.

`metis engine run` runs steps 2 and 3 together. The code is a Python monorepo. The step
this document concerns lives in the `metis-engine` package, under
`packages/engine/src/metis/engine/simulation/`.

```
  1. specify                          2. simulate (this document)          3. evaluate
 ┌──────────────────────┐   inputs   ┌────────────────────────┐  outputs  ┌──────────────────────┐
 │ specification.yaml   │──────────▶ │ persona × scenario ×   │─────────▶ │ record.json          │
 │ fixtures/            │            │ trial  →  conversation │           │   + Langfuse traces  │
 └──────────────────────┘            │ with the target        │           │   joined on          │
  hand-written, or from              └───────────┬────────────┘           │   target_session_id  │
  metis wizard / apps/web                        │                        └──────────┬───────────┘
                                                 ▼                                   ▼
                                            target ──traces──▶ Langfuse      metrics → report
```

Simulation does not score anything. It holds conversations with the target, and the
target writes its own traces to Langfuse. Simulation then hands evaluation two things:
the target's session ID, so evaluation can find those traces, and a few facts that only
simulation knows, such as why the conversation stopped and which files changed hands.

The target system belongs to another team. METIS does not control its API, its UI, its
tracing or its release schedule. Orca, the current target, is built and documented by
the Orca team, who own its published API specification and contribute runner updates to
METIS. Any design therefore has two sets of users: the METIS user who runs experiments,
and the target team that has to make its system reachable.

### Inputs

All inputs come from an experiment directory containing `specification.yaml` and
`fixtures/`. The CLI copies that directory to `experiments/<id>-<timestamp>/inputs/`
before it runs anything.

| Input | Where it lives today | What it is |
| --- | --- | --- |
| **Persona** | `specification.personas[]` (`id`, `name`, `description`) | Free-text description of who the simulated user is and how they behave. |
| **Scenario** | `specification.scenarios[]` (`id`, `name`, `description`) | Free-text description of what the user is trying to achieve. There is no structured success condition. |
| **Fixtures** | `fixtures/` directory, with a per-task allow-list in `tasks[].fixtures` | Files the user may upload. Their content descriptions are LLM-summarised once per experiment, or supplied in `fixture_content_descriptions`. |
| **Task** | `specification.tasks[]` | Binds one scenario to one persona and some fixtures. It also carries the run budget: `num_trials`, `max_turns`, `timeout_minutes`, `response_wait_ms` and `max_run_retries`. |
| **Target binding** | `runner_factory_ref` (a Python FQN) plus runner env vars (`ORCA_API_URL`, `ORCA_API_KEY`, …) | Selects the runner class that talks to the target. |
| **User-agent LLM** | `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `USER_AGENT_MODEL`, … | The model that plays the persona. |

The unit of work is a **trial**, meaning one task × one trial index. Each trial produces
one conversation, which becomes one target session.

### Outputs

```
experiments/<spec-id>-<timestamp>/
├── inputs/                         # verbatim copy of the input directory
├── trials/<task>-<persona>-<n>/
│   ├── record.json                 # the trial record handed to evaluate and the report
│   └── artifacts/                  # files the target delivered, plus a manifest
└── logs/
```

Traces are not an output of simulation. Metrics are computed from the target's Langfuse
traces, not from the simulation's own record of the conversation. `record.json` is the
current hand-off format, and its shape may change for a good reason (see Constraints).

## 2. Current system

```
CLI ─▶ run_experiment ─▶ RunnerFactory.start()
                          ├─ worker 0 ─▶ for each trial (fixed round-robin slice):
                          ├─ worker 1        factory.create() → Runner
                          └─ worker N        Orchestrator.run():
                                               UserAgent.generate_opening()
                                               loop: Runner.send_turn(msg, actions) → Observation
                                                     UserAgent.generate_response(observation)
                                               until goal_achieved | giving_up | max_turns | timeout
                                             write record.json + artifacts
```

- **Orchestrator** (`simulation/orchestrator.py`) runs the turn loop, applies the
  stopping rules, withholds uploads that are not on the allow-list, summarises each
  delivered artefact with an LLM, and assembles the record.
- **UserAgent** (`simulation/user_agent/`) makes one structured-output LLM call per turn
  and returns `message`, `decision` (`continue` / `goal_achieved` / `giving_up`) and a
  list of typed `actions` (`upload_file`, `button_click`, `form_fill`), each naming a
  slot ID the runner offered on the previous turn.
- **Runner** (`simulation/runner.py`) is an ABC with `setup()`, `send_turn(message,
  actions) -> Observation`, `teardown()` and `get_session_id()`. A `RunnerFactory` holds
  resources shared across trials, such as a browser process or a rate limiter. Every
  runner must follow the rules in `docs/runner-contract.md`.
- **Runners**: `orca_api` drives Orca's REST API, and `orca_playwright` drives Orca's web
  UI. Both are specific to Orca. There is no generic runner.
- **Retries** happen at the trial level. A recoverable failure throws the whole trial away
  and starts it again from turn 1.

### Where to look in the code

- `packages/engine/src/metis/engine/cli.py`: the `simulate`, `run` and `evaluate` entry
  points, and `_classify_resume_trials`
- `packages/engine/src/metis/engine/simulation/`: `experiment.py`, `orchestrator.py`,
  `runner.py`, `types.py`, `exceptions.py`, `user_agent/`, `runners/`
- `packages/engine/src/metis/engine/simulation/README.md`: the current architecture
- `packages/engine/src/metis/engine/simulation/runners/orca_api/README.md`: Orca API turn
  lifecycle
- `docs/runner-contract.md`: the runner invariants
- `packages/engine/src/metis/engine/extractor/langfuse.py`: Langfuse fetch, and how
  artefacts are matched to traces
- `packages/engine/src/metis/engine/reporting/_report.py`: how the report reads
  `record.json`
- `packages/library/src/metis/library/metrics/`: what metrics read from test-case
  metadata
- `packages/engine/example-experiment/`: example specifications to validate against

## 3. Problem

### Observed by the team

These come from the team's experience operating `simulate`:

1. **The runners are brittle.** Small changes in the target's UI or API behaviour break
   runs, and each fix tends to add another special case.
2. **Every new target needs a new runner written in Python.** Someone has to write and
   maintain a `Runner` subclass, and possibly a `RunnerFactory`, against a 283-line
   normative contract. Because the target belongs to another team, that someone is
   either a METIS developer chasing another team's changes, or the target team writing
   METIS internals. Either way it is the largest barrier to METIS being usable by
   anyone other than its own developers.

### Measured from past experiments

There are 281 trial records from seven Orca experiments run between 2026-08-20 and
2026-10-08. Six experiments (227 trials) used `OrcaApiRunner`. One (54 trials) used the
Playwright runner. For every trial that did not reach `goal_achieved`, the cause below
comes from the run's `record.json` and its per-run log, and from the team's own
write-ups for two of the experiments. These experiment directories are local and
git-ignored, so they are not in the repository; the numbers here are the summary.

| Outcome | Trials | Share | What actually happened |
| --- | --- | --- | --- |
| `goal_achieved` | 190 | 68% | |
| `user_abandoned` | 43 | 15% | see below. Almost none were genuine judgements of the product |
| `timeout` | 24 | 9% | the 15-minute trial limit. Mostly slow Orca turns in the heaviest scenarios (`multi-agent-pipeline`, `constrained-analysis`), where individual turns waited out the 5-minute response limit |
| `system_error` | 18 | 6% | 9 user-agent LLM failures (connection errors, a 403, truncated output, an invalid structured response); 4 Orca `404`s for a session or turn that had expired; 4 crashes whose exception was never recorded; 1 Playwright selector timeout |
| `max_turns`, `target_exhausted` | 6 | 2% | the user agent looping on a request Orca could not progress; one Orca per-call input cap |

Four findings matter more than the outcome counts:

1. **Crashes are not the main problem.** Only about 9 of 281 trials (3%) crashed
   because of a runner or the target's transport. Half of all `system_error`s came from
   the user-agent LLM, not from a runner.
2. **The worst failures are silent and look like product behaviour.** In the Playwright
   experiment, 8 trials ended with the user agent giving up because, in its words, "no
   upload control or file-upload action is available to me". Orca reported that the
   session had no files, so the scenario's files never arrived, and the browser runner
   offers the user agent no upload slot to try again with. Those trials were recorded as
   the user abandoning Orca. That experiment ran on August's code, so the specific bug
   may since have been fixed, but nothing would detect a new one. In the 2026-09-03 experiment, Orca's
   data-analysis allowance ran out, and 29 trials (26 abandoned, 2 at the turn limit, 1
   timed out) went on talking to a target that could not do the work. Nothing in
   simulation noticed. The team's write-up concluded that the run was "largely invalid"
   for most of its scenarios.
3. **The user agent argues with file descriptions instead of files.** In the 2026-10-06
   experiment, 3 of the 4 abandonments were the user agent disputing Orca's reading of an
   uploaded file, because the LLM-written description it had been given said something
   different (for example, "152 rows" against Orca's "200 rows"). This is the
   prompt-only workaround in #310 showing up as a product failure.
4. **Failures are hard to diagnose after the fact.** Four crashes in the 2026-09-02
   experiment left no exception type or traceback in the record or log (#306). Retries
   do not help with persistent faults: two trials in 2026-09-30 used all three attempts
   within five seconds on the same expired-turn `404`.

The trials that ended `goal_achieved` were not checked. Because the user agent decides that
outcome itself, the 68% figure is an upper bound on trials that achieved their goal.

### Measured from the code

The code shows the same picture:

| What | Size |
| --- | --- |
| `runners/orca_api/` | 2,331 lines |
| `runners/orca_playwright/` | 2,188 lines |
| Everything else in `simulation/` (orchestrator, user agent, types, contract checks) | 3,232 lines |
| `docs/runner-contract.md` | 283 lines of normative rules and edge cases |
| Exception classes in `simulation/exceptions.py` | 13, in two recovery families |

Supporting one target costs more code than the whole runner-agnostic framework, and
that one target needed two runners. The contract and the exception hierarchy exist
largely to manage how runners fail. Orca-specific knowledge has also leaked into shared
code. For example, the user-agent system prompt explains Orca's form semantics and tells
the user agent to "ALWAYS select Fast (Claude Haiku)".

### Suspected causes (to validate, not assume)

These are hypotheses from reading the code. A proposal should say which ones it
addresses, and how it would confirm each one.

*Complexity and brittleness*

1. **The runner interface is too wide.** One `send_turn` call carries a message plus a
   list of typed actions. The contract therefore needs positional bookkeeping, a
   verdict per action, and caller-side withholding, and each runner must turn
   target-specific UI or API state into `ActionSlot`s for the user agent to choose from.
2. **Target knowledge is hand-coded.** Element resolution, form mapping, upload flows,
   polling and artefact download are written by hand for each target, so every change in
   the target is a code change in METIS.
3. **Too many failure modes are surfaced.** Thirteen exception types across two recovery
   families, together with escalation rules, make the failure behaviour hard to reason
   about.

*Effectiveness*

4. **The user agent grades itself.** The user agent decides when the run ends
   (`goal_achieved`), with no independent check.
5. **The simulation does not aim at what will be measured.** The user agent pursues the
   scenario goal and is never told which behaviours evaluation will score.
6. **Scenarios are unstructured.** Free text cannot express branching or a checkable
   end state.

*Efficiency*

7. **Static scheduling.** Trials are split round-robin before the run starts, so one slow
   trial holds up its whole worker slice while other workers sit idle.
8. **Coarse retries.** A failure on turn 9 re-runs turns 1–8.
9. **Fixed trial counts.** `num_trials` is fixed in advance, with no early stopping.

The headline problems are the need for a runner per target, and runners that fail
silently in ways that look like product behaviour, rather than runners that crash.
Proposals should prioritise those. The other effectiveness and efficiency causes are
secondary, except that the user agent grading itself (cause 4) limits how far any
success rate can be trusted.

## 4. Goals and success criteria

The proposal will be judged on these criteria, roughly in priority order:

1. **A new target needs no new Python.** Pointing METIS at a new agentic system should
   take configuration only, such as a base URL, credentials, an API specification or a
   start page, and at most a short natural-language description. Measure this as the
   lines of target-specific code and configuration needed to support Orca, counting
   both what the METIS user writes and what the target team must publish.
2. **Reliability, including silent failures.** Fewer trials should end in
   `system_error`, and far fewer should end in a way that is wrongly blamed on the
   target: a file that was never uploaded, or a target that could no longer do the work.
   Simulation should notice when a trial has stopped being a valid test, and record
   that rather than an ordinary outcome. The proposal should define how this will be
   measured against today's runners on the same specification.
3. **Simplicity.** There should be noticeably less framework code, contract surface and
   failure-mode surface than today. Where the design keeps a guarantee from
   `docs/runner-contract.md`, it should keep it in the simplest form that still holds.
4. **Fidelity of evidence.** What the record says happened must be what actually
   happened. The design must not let any component, LLM-based or not, report an action
   as done when it was not: the record states facts, never interpretations.
5. **Cost and speed.** Wall-clock time and LLM spend per trial should be no worse than
   today without a stated reason. A design that adds LLM calls should show what it buys.

## 5. Constraints

### Decisions already made

These settle questions a proposal would otherwise have to guess at:

1. **The design is target-agnostic; the first implementation is HTTP against Orca.**
   The user simulation must not assume any one target or transport. The proposal should
   show that a browser target, or any other transport, fits the same design. It only has
   to *implement* one: an HTTP runner against Orca's REST API, which is enough to
   validate it.
2. **The specification schema may change.** A proposal may add to or change
   `specification.yaml` (for example, structured success conditions in scenarios, or
   adaptive trial counts), provided it says what changes and how existing
   specifications migrate. The wizard and `apps/web` write specifications, so a change
   there is a cost to count.
3. **The user agent should default to natural-language actions.** Ideally the user agent
   says what it wants the way a real user would ("upload file ABC.pdf", "pick the
   second option"), instead of emitting typed actions that name slot IDs. The point is
   to keep the user agent itself simple: it should not need an action schema, an
   `ActionSlot` protocol, or a catalogue of per-target action types to track. This holds
   whether or not the proposal adopts a runner agent (see Ideas to consider) — something
   still has to turn natural language into transport calls, and the proposal must say
   what. A design that keeps typed actions on the user agent should justify why plain
   language is not enough.

### Hard constraints

- The `fixtures/` layout stays as it is.
- Simulation must not alter or stand in for the target's traces. The target writes its
  own, simulation records the session ID that links to them. Simulation may emit its
  own spans (the user agent, the runner, any runner agent, and so on), but they must
  stay clearly separate from the target's, so that nothing METIS emits is ever mistaken
  for the target's behaviour.
- `metis engine evaluate` must keep working, either unchanged or changed in the same
  proposal with a migration.
- METIS does not control the target. Asking a target team to *publish* something that
  describes their system, such as an API specification or a short profile, is a small
  request. Asking them to build something for METIS, such as a new endpoint or a change
  in behaviour, is a large one. A design may make either request, but it must state
  each one, and the comparison must count it as a cost, because people outside METIS
  have to agree to it and then keep it up to date.

### Soft constraints

`record.json` and the report can change for a good reason. To avoid over-engineering the
record, design it around what is actually read downstream:

**What `metis engine evaluate` reads** (`cli.py` `evaluate`, `extractor/langfuse.py`,
`metis.library.metrics`). It uses only eight fields:

| Field | Why evaluate needs it |
| --- | --- |
| `target_session_id` | the key for fetching the session's traces from Langfuse; a record without it is skipped |
| `config.metric_refs` | which metrics to run. They are read from the record, not from the specification; a record without them is skipped |
| `config.task_id` | looks up the resolved task in the specification, which is passed to metrics as `scenario` |
| `config.persona` | looks up the persona, which is passed to metrics as metadata |
| `config.scenario` | used only for the progress label |
| `config.trial_index` | attributes the result to its trial |
| `outcome.stop_reason` | passed to metrics. `AbandonmentMetric` scores on it directly |
| `artifacts[]` | injected into each trace's test case. Metrics use `source`, `state`, `path` and `at_turn`, and see an artefact on trace *i* only if `at_turn ≤ i` |

`evaluate` never reads `conversation[]`. Turn-counting metrics such as
`TurnBudgetMetric` read `total_turns`, which the extractor sets to the number of
Langfuse traces in the session, not the number of turns in the record.

**What the HTML report reads** (`reporting/_report.py`), only for display: `outcome.total_turns`, `outcome.duration_seconds`, `attempt_number`, and from each
`conversation[]` entry its `turn_number`, `user_message`, `target_response.text`,
`target_response.response_notices`, and the `succeeded` / `withheld` / `detail` /
`action_index` of each `action_results` row. The last two decide whether a failure is
blamed on the product or on METIS.

**What `--resume` reads**: `outcome.stop_reason` (to redo `system_error` trials), and
whether the file loads at all.

**Nothing downstream reads** `user_ui_actions`, `diagnostics`, `duration_ms`,
`timestamp`, `prior_failures`, `max_allowed_attempts`, or most `Artifact` fields
(`digest`, `external_id`, `content_description`, …). These are for humans debugging a
run.

What follows from this:

- **The real contract is small.** It is a session ID, the metrics to run, attribution
  (task, trial, persona), a stop reason, and artefacts with the turn they appeared on.
  The proposal should aim for the smallest record that satisfies these readers, and
  justify anything it adds beyond that.
- **`at_turn` is a hidden coupling.** Artefacts are matched to Langfuse traces by
  comparing the simulation's `at_turn` with the trace's position in the session. That
  only works if a simulation turn lines up one to one with a target trace. Any change to
  what a turn means must keep that alignment, or change how the extractor matches
  artefacts.
- **The report needs blame attribution, not a fixed row shape.** It must still tell a
  product failure from a METIS failure, but the current shape of `action_results` is not
  required.

```
   hard                                    change with the report          free to redesign
 ┌──────────────────────────────────────┐  ┌─────────────────────────────┐  ┌───────────────────────────┐
 │ fixtures/ layout                     │  │ record fields the report    │  │ orchestrator / turn loop  │
 │ target's traces stay the target's    │  │ displays (conversation,     │  │ user-agent prompts        │
 │ the 8 record fields evaluate reads,  │  │ action results, notices,    │  │ scheduling, retries       │
 │   or evaluate changed to match       │  │ total_turns, duration,      │  │ Runner interface          │
 │ target_session_id ↔ Langfuse join    │  │ attempt_number)             │  │ target binding            │
 │ at_turn ↔ trace-position alignment   │  │ specification schema, with  │  │ record fields nobody reads│
 │                                      │  │   a migration               │  │ METIS's own trace spans   │
 └──────────────────────────────────────┘  └─────────────────────────────┘  └───────────────────────────┘
```

The record is not a published schema (unlike `report.schema.json`), so there are no
outside consumers to migrate.

## 6. Ideas to consider

These are ideas the team has discussed. They are starting points, not requirements and
not a shortlist. The proposal may use any of them, combine them, or set them aside.

### A runner agent behind a thin `Runner`

The simulation is driven by an **orchestrator** (our name for the user-simulation
logic). It owns the persona, the scenario, the fixtures, the stopping rules and the
record, and it reaches the target only through a `Runner`:

- `Runner` is an abstract base class with an abstract method such as `send_turn()`.
- **Each call performs exactly one action.** The result of a call is then the result of
  that action, which would remove the need for positional bookkeeping altogether.
- **Actions are natural language.** This part is already decided (see Decisions already
  made), not specific to this idea: the user agent says what it wants the way a real
  user would ("Help me upload the quarterly report"), instead of emitting typed actions
  that name slot IDs. In this idea specifically, that removes the action union, the
  `ActionSlot` protocol, and the target-specific instructions from the user-agent
  prompt.
- **The `Runner` relies on a *runner agent*.** This is an LLM agent that turns the
  natural-language action into transport calls. For example, an HTTP runner agent reads
  the target's REST API specification (OpenAPI) and works out the requests, and a
  browser runner agent reads the page and decides what to click or type. The `Runner`
  itself keeps lifecycle, credentials, guardrails and evidence capture.
- There could be several generic implementations, such as `HttpRunner` for REST APIs and
  `PlaywrightRunner` for web UIs, configured per target rather than subclassed.

```
 user agent                          Runner                          target system
┌──────────────────────┐  one NL   ┌──────────────────────────────┐
│ "Help me upload the  │  action   │ runner agent (LLM)           │  HTTP requests /
│  quarterly report"   │─────────▶ │   reads API spec / page      │  browser actions
│                      │           │   plans transport calls      │─────────────────▶
│                      │◀───────── │ Runner shell                 │◀─────────────────
└──────────────────────┘ observ-   │   auth, allow-lists, limits, │  replies, files,
                         ation     │   raw evidence capture       │  session ID
                                   └──────────────────────────────┘
```

In this picture the **user agent** decides *what* the user wants next, and the **runner
agent** decides *how* to make that happen on this target. The user agent would never see
API details, and the runner agent would never make the user agent's decisions, such as giving up.

#### Example: a Playwright runner

A browser runner is where a runner agent would simplify things most. A web UI can show
almost anything: buttons, forms, dropdowns, radio groups, dialogs, file pickers, in any
layout and with any labels. Without a runner agent, every one of those possibilities
has to be written down ahead of time as code in the runner class. With one, the
`Runner` class shrinks to three steps:

1. **Read the page.** Capture the current HTML, or the accessibility tree, plus a
   screenshot if useful.
2. **Pass it to the runner agent**, together with the user agent's natural-language
   action ("Choose the detailed report option and submit").
3. **Let the runner agent decide** which button to click, which field to fill and which
   form to submit, out of whatever the page actually offers. The Runner then performs
   those steps through Playwright and reports what happened.

```
 without a runner agent                          with a runner agent
┌───────────────────────────────────────┐       ┌───────────────────────────────────────┐
│ Runner class (per target, hand-coded) │       │ Runner class (generic)                │
│  selectors for the message box        │       │  1. read HTML / accessibility tree    │
│  selectors for submit buttons         │       │  2. pass it + the NL action to the    │
│  logic per form-control type          │       │     runner agent                      │
│  upload flow, login flow              │       │  3. perform the steps it chooses,     │
│  page-state → ActionSlot translation  │       │     record what happened              │
│  fallbacks for anything unforeseen    │       │                                       │
└───────────────────────────────────────┘       └───────────────────────────────────────┘
   every new screen = new code                     every new screen = nothing new
```

Today's `orca_playwright` runner (about 2,200 lines) shows the left-hand side in
practice. It makes about 40 hard-coded element lookups. Its form handling
(`_page_actions.py`, `auto_fill_and_submit`) looks for buttons labelled exactly
"Submit", "Continue", "Confirm Theme" or "Confirm", and treats "Select an option..." as
the placeholder in a dropdown. Whenever the user agent's actions did not include a click on a
submit button, the runner fills the form itself and submits it. It picks the first real
option in each empty dropdown, checks the first radio button when none is checked, and
fills empty text boxes with their placeholder text or "General audience". That puts choices into the conversation that the user agent never made. Each of these is knowledge about one
target's current screens. Any change to the target's UI breaks it, and it does not carry
over to another target.

The same reasoning applies to an HTTP runner, where the runner agent reads the OpenAPI
specification instead of the HTML. The gain is largest in the browser, though, because a
UI's possibilities are open-ended, while an API's are listed in its specification.

#### What the target has to provide

A runner agent removes target knowledge from METIS's code, but that knowledge still has
to come from somewhere. A runner agent can only work out what its inputs tell it, so
this idea moves some of the burden onto the target: the target and METIS have to agree
on what the target exposes and how.

For a REST API target, the minimum is an API specification that is complete, accurate
and machine-readable, preferably in OpenAPI format, and that the runner can fetch
without help. Orca already publishes one: an OpenAPI 3.1 document at
`/api/v1/openapi.json`, which needs no API key. A target with no specification, or with
an out-of-date one, would fall back to hand-written configuration or code.

A specification describes the *shape* of each request. Orca shows that the runner also
needs the *protocol*, and much of that is behaviour a schema does not capture:

| What the runner must know | How Orca does it | In an OpenAPI schema? |
| --- | --- | --- |
| How to send a message and get the reply | `POST /chat` returns `202` with a `turnId`; the reply arrives by polling `GET /chat/{turnId}` until `status` is no longer `running` | Partly. The endpoints are listed, but "poll until settled" is prose |
| How a session starts | minted by the first `POST /chat` that carries no `sessionId`; `POST /sessions` is never needed | Only as prose, if at all |
| Which ID is the Langfuse session ID | Orca's `sessionId`, which is also the Langfuse `session_id` | No. This is a fact about the target's tracing, not its API |
| How uploads work | upload first with `POST /files`, then attach the `fileId` to a chat turn | Partly |
| Which requests are invalid together | a turn carries `message` or `formAnswers`, never both and never neither | Only as prose |
| Rate limits, and which endpoints are safe to call | separate submit and read limits; some endpoints delete data | Rarely |

The Langfuse row matters most. Evaluation depends on it entirely, and no API
specification will ever state it, so the target has to declare it some other way.

For a browser target, the agreement is looser but still exists: a way to log in that an
automated browser can complete, a page structure stable enough to read, and a way to
find the session ID after the first message.

The proposal should therefore define what a target must provide for this idea to work.
That could be a short "target profile" holding the specification URL, authentication,
how the session ID maps to Langfuse, and the behaviours that schemas leave out. It
should also say what happens when a target cannot provide one.

Because the target belongs to another team, this is an agreement between teams, not
just a file format. The target team would own its specification and profile and keep
them in step with its releases, in the same way the Orca team already owns Orca's
published API docs. METIS would own the format and the runner that reads it. The
proposal should say:

- what the target team commits to, kept as small as possible;
- how METIS finds out the profile has gone stale, for example by checking it against
  the live specification at the start of each experiment, rather than failing midway
  through a run;
- how a version change on the target side (Orca puts breaking changes under a new
  version prefix such as `/api/v2`) reaches METIS.

A smaller commitment is easier to agree and easier to keep. That is one reason to
prefer designs that learn as much as possible from what a target already publishes.

Things worth thinking about if this idea is used:

- **Reliability of the runner agent.** It can misread the specification, build a wrong
  request, or claim success that did not happen. Building the observation from raw
  transport evidence (status codes, response bodies, screenshots), rather than from the
  runner agent's own summary, is one way to protect goal 4.
- **Guardrails.** With natural-language actions, the orchestrator can no longer check the
  fixture allow-list before dispatch, so something else has to enforce it, along with
  limits such as never calling destructive endpoints.
- **Cost, speed and reproducibility.** It adds a second non-deterministic LLM on every
  action. One mitigation is to plan once per target and cache the plan.
- **Target-coupled actions.** Some targets couple actions. Orca, for example, accepts
  either a message or form answers on one submit, never both.

### Other directions

Some other directions that came up:

- **A declarative adapter.** A generic `HttpRunner` driven by a small per-target
  configuration that maps "send message", "upload file", "read reply" and "get session
  ID" onto endpoints. This is deterministic and cheap, but someone has to write the
  mapping.
- **Compile once, replay.** An agent explores the target once and generates an adapter
  that a human reviews. Trials then run with no LLM in the transport path.
- **A target-side protocol.** METIS defines a minimal chat endpoint (or MCP server) that
  the target team exposes, which moves the integration work to the target team. This is
  the largest request a design can make of another team (see Constraints).
- **A simpler version of today's design.** Keep hand-written runners, but narrow the
  interface and contract until writing one is a small job.

### What counts as a turn

If one user-agent intent can take several runner calls, "turn" needs a precise definition.
It is the unit for `max_turns`, for `conversation[]` and for the report, and through
`at_turn` it is how artefacts are matched to traces. Two definitions that came up:

| Definition | A turn is… | Consequence |
| --- | --- | --- |
| **One user-agent span** | one decision of the user agent, however many runner calls it needs | Matches what a human would call a turn. It needs new instrumentation, because simulation emits no trace spans today: only the target is traced. Simulation may emit its own, kept separate from the target's (see Hard constraints). |
| **One `send_turn()` call** | one runner call, which is one action | Simple and already measurable. One user-agent intent may count as several turns, which shifts what `max_turns` means. |

The target's traces define `total_turns` for the metrics, so whatever definition is
used has to stay aligned with them (see Constraints).

## 7. Open questions

1. How do we measure whether a simulated conversation is *useful* for evaluation?
   Candidates: the fraction of trials in which each behaviour being measured became
   observable, the rate of false `goal_achieved`, and turns and cost per useful trial.
2. Can a runner agent working only from an OpenAPI specification, or only from a web
   page, drive a target it has never seen? How often does it get an action wrong, and
   can a wrong action be detected from transport evidence alone? What must a target
   provide beyond its specification (see What the target has to provide), and how many
   real targets can provide it?
3. Which guarantees in `docs/runner-contract.md` still matter in the new design, in what
   form, and which ones disappear? (Lessons behind them include a silently dropped
   action, #320; a turn re-sent without knowing whether the first send landed; and
   conflating "the target offered nothing" with "nobody checked what was offered".)
4. Who decides when a trial ends: the user agent, an independent judge, or a structured
   success condition?
5. Should the user agent, or a separate planner, be told the behaviours under test, and how
   do we aim at a behaviour without leading the target unrealistically?
6. How should scheduling and retries work? Compare a work queue with static slices, and
   resuming from the last good turn with replaying the whole trial.
7. What run metadata is needed so that trials stay comparable when the user-agent LLM, a
   runner agent, or the target's own model varies? (Orca, for example, silently swaps in
   a cheaper model once a shared allowance is spent.)

## 8. What the proposal must contain

1. **A summary**: the recommended design in one paragraph, and which goals in section 4
   it meets.
2. **The design**: the orchestrator, the `Runner` interface (signatures), the role of any
   LLM agents, and how each input in section 1 becomes each output. Include ASCII
   diagrams of the components and of one trial's sequence of calls. Show that the design
   is target-agnostic: how an HTTP runner (implemented, against Orca) and a browser
   runner (not implemented) would both fit it. Show the shape of a user-agent action and
   confirm it stays natural language (see Decisions already made #3), or justify why not.
3. **Specification and tracing changes**: any change to `specification.yaml`, with its
   migration, and any spans simulation emits, with how they are kept apart from the
   target's traces.
4. **The target binding**: exactly what a user writes to point METIS at Orca, shown in
   full, and what they would write for a hypothetical second target. Say which parts
   the METIS user writes and which parts the target team must publish and maintain.
5. **Options considered**: the main options weighed, including any ideas from section 6
   that were used or set aside, and why the recommended design was chosen, judged
   against the goals in section 4.
6. **Failure model**: what can go wrong on each turn, who detects it, what is recorded,
   and what is retried. For each rule in `docs/runner-contract.md`, say whether the
   design keeps it, makes it unnecessary, or drops it, and why.
7. **Record and downstream changes**: the proposed `record.json` fields, each traced to
   a reader from section 5, and every change needed in `evaluate`, the extractor, the
   metrics or the report.
8. **Turn definition**: the chosen definition and how it stays aligned with target
   traces.
9. **Validation plan**: the experiments that would confirm the design, using the HTTP
   runner against Orca and compared with today's `simulate` on
   `packages/engine/example-experiment/`, with the metrics to
   collect (failure rate, retries, wall-clock time, LLM cost, usefulness from question 1).
10. **Migration**: how to get from today's code to the design, what is deleted, and what
   happens to the existing Orca runners.
11. **Risks and open questions** the proposal could not resolve.

## 9. Non-goals

- Evaluation, metrics and the report, except where the design forces a change.
- Collecting or altering the target's traces. The target writes its own; simulation may
  add separate spans of its own.
- Writing specifications (step 1), whether by hand, with `metis wizard`, or in `apps/web`.
